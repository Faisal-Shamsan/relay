## Completed

- Project specification reviewed.
- Engineering workflow defined.
- Repository control structure created.
- M1: one sequential step. A crash before completion restarts the attempt. A later attempt completes. Replay returns the stored result without calling the user function. A duplicate completion returns the stored receipt.
- M2: heartbeat, explicit release, and a reaper. A stale owner cannot renew or write after expiry or a newer grant. Client clocks do not choose deadlines.
- M3: a crash after an external effect and before completion runs the callback again with the same provider key. Finish-run crashes before commit roll back together. A changed body with the same operation id conflicts.
- M4: duplicate step keys fail before the second callback. Reordered, removed, and inserted commands diverge before the new callback. A captured value with the same command shape is not detected.
- M5: a parallel group declares every child in one transaction. A completed child is memoized, an active child restarts, and a failed child stays exhausted. Reversed completion order does not change discovery ordinals or the returned result order.
- M6: an identical trigger returns the same run, and a different intent conflicts. A pinned v1 run stays pending when only a v2 worker is live. Direct invalid writes do not persist. Exceeding the stored recovery budget fails the run instead of starting another attempt.
- M7: the remaining Phase 1 failpoint hooks roll back with the transaction. Projection verification reports drift without rewriting history. Run and event reads are available. A dropped database connection is resolved from the receipt, and the failover recovery point is disclosed. The failure demo completes 100 runs.
- M8: a durable per-run stream log. A retried batch keeps one sequence. A conflicting or gapped batch writes nothing. Completion requires the flushed batch number. A crash after that flush supersedes only the interrupted attempt, and a crash after completion does not start another. A sibling's chunks stay in place.
- M9: live SSE on the stream sequence. A shared listener only wakes readers. A client that reconnects across supersession matches one that stayed connected. A missed notification is recovered by catch-up or polling. A client that falls behind a bounded queue is disconnected, and a later batch still commits.
- M10: seven-day stream retention. A terminal run's stream rows are deleted in the same locked transaction that sets `stream_expired_at`. The workflow history, step result, and stream sequence counter stay. A reader gets `410 StreamExpired` with the stored result, including a connection that was already open. An active run is left alone.
- M11: explicit step inputs. `ctx.step(name, {input}, fn)` and a parallel child's `input` persist the normalized value and its canonical hash with the command. Replay compares that fingerprint before a memoized return or another attempt. An omitted input and an explicit `null` differ. The callback receives a frozen clone. A closure change with the same command shape is still not detected.
- M12: journaled helpers. `ctx.now`, `ctx.random`, and `ctx.uuid` require a key. The server draws the value once, after the run lock, and stores it on the command. Replay and an identical request return that value. A different key at the recorded position is nondeterminism. The same helper key twice in one evaluation is rejected. A helper inside a step callback is rejected.
- M13: durable timers. `ctx.sleep(key, durationMs)` records the duration and one database wakeup. A positive duration releases the lease and leaves the run sleeping. Zero completes in that same transaction. The scheduler copies the recorded wakeup into `TimerFired` and makes the run ready. A crash or a second scheduler does not write a second outcome or a new deadline. Replay of a fired timer does not schedule it again.
- M14: explicit retries. `ctx.step(name, {retry}, fn)` stores the policy with the command. A retryable failure records one database delay, including jitter, and does not show that error to the workflow. A positive delay releases the worker only when no sibling callback is still running. The scheduler wakes the run without choosing a new deadline. Exhaustion throws `StepExecutionError`. An unhandled exhaustion fails the run and appears in `relay_failed_runs`. A handled failure that finishes the run does not. Without a policy, a callback failure is still not retried.
- M15: workflow lint and a publishable SDK. `lintWorkflow` reports a direct clock, random, UUID, environment, I/O, shared global, or `Promise` fan-out outside a step callback. The same calls inside a step or parallel child are allowed. A call hidden in another function is not reported. `@relay/sdk` and `@relay/protocol` pack as version 0.1.0. The public entry does not export a failpoint loader or a Phase 3 or Phase 4 API. The server package stays private.
- M16: projection rebuild. `relay_rebuild_projections` rewrites commands, steps, attempts, and the business run fields from `run_events`, then verifies in the same transaction. A live lease is refused before any write. Fence, allocators, queue, receipts, and the stream log stay put. A second rebuild of an already-correct run does not move them. The CLI is `projections rebuild`. F36 is `packages/server/test/rebuild.test.ts`.
- M17: inspection reads. `GET /v1/runs` filters the seeded tenant by state, workflow, and version. The cursor is a validated decimal offset, not a SQL fragment. `state=failed` is that filter over run rows. It is not a second queue and it does not redrive. `GET /v1/runs/:id/steps` returns each step and its attempts, and includes `input` only when the command recorded one. The proof is `packages/server/test/reads.test.ts`.
- M18: operational metrics. `GET /v1/metrics` reports current gauges: runs by state, pending runs by pinned workflow version, and live compatible workers by version. A pending run whose worker has expired stays visible with zero live workers for that version. There is no cost series. Each request exports one span with the request id and, when the request has them, the run, fence, step, and attempt. Replay and a first callback stay different labels. If `RELAY_OTEL_ENDPOINT` is unset or the export fails, the transition still commits, and the trace is not stored. The proof is the metrics test in `packages/server/test/reads.test.ts`.
- M19: dashboard. `relay-dashboard` is a Next.js app. It reads the run list, run detail, steps, events, and the SSE stream. It does not import `pg`, the server, or the SDK, and it has no database URL. The list filters by state, workflow, and version. A run shows its pinned version, state, output or error, and ownership. The timeline keeps business attempts, lease epochs, retries, and abandoned attempts distinct. An input appears only when the command recorded one. There is no signal, cancel, or rebuild control. The three-minute debugging recording is a manual check and is not generated. The source check is `packages/server/test/dashboard.test.ts`.
- M20: measurement note. The existing 100-run demo prints activation time and history bytes for that run. It does not measure stream catch-up, 1,000 runs, 10,000 runs, Postgres CPU, or a separate replay duration. No cache and no larger run were added. The note is in `tests/demo.test.ts` and `README.md`.
- M21: tenant API keys and row security. `Authorization: Bearer` selects one tenant. The database stores only the SHA-256 of a key. A client key can create, read, stream, signal, and cancel. A worker key can register, lease, heartbeat, and append. A missing, revoked, or wrong-kind key is 401. Another tenant's run is the same 404 as a missing run. `relay_app` with tenant B's setting cannot select tenant A's rows, and a direct table write is still rejected. The dashboard attaches `RELAY_API_KEY` on the server. F38 is `packages/server/test/auth.test.ts`. The decisions are ADR 0017 and ADR 0018.
- M22: same-priority tenant fairness. `relay_grant_lease` still orders by priority first, then by the oldest `tenants.last_granted_at`, then by availability and run id. The grant updates that timestamp after the run lock. Rebuild does not move it. A higher priority still wins, so a lower priority can keep waiting. That order is not a throughput result. The proof is `packages/server/test/fairness.test.ts`.
- M23: durable signal inbox. `POST /v1/runs/:id/signal` appends `SignalReceived` and an inbox row. The same idempotency key and payload replay the stored ingress sequence. A different payload conflicts. An early signal remains until a wait consumes it. A terminal run accepts no new signal. Rebuild restores the inbox and does not move the fence, queue, or receipts. The proof is `packages/server/test/signals.test.ts`.
- M24: named waits. `ctx.waitForEvent(name, {timeoutMs})` is one top-level command. An early signal is consumed oldest-first, and a second signal of that name stays. A zero timeout with no signal records one timeout and does not park. A signal and a firing scheduler produce one `WaitResolved`. A second fire does not write another. Replay returns the stored result and does not park again. A wait inside a step callback is rejected. The proof is `tests/waits.test.ts`.
- M25: cancellation versus completion. If completion commits first, cancel returns that completed run and writes no `RunCancelled`. If cancel commits first, the run is `cancelled`, output and error stay null, the queue row is removed, the unfinished attempt is abandoned, and one `run_terminal` stream control is written. The later completion is rejected. History remains readable. A callback may already have performed an external effect; cancellation does not undo it. The callback's existing abort signal is the cooperative abort. Timer, retry, and wait firing do not wake a cancelled run. F37 is `tests/waits.test.ts` and `tests/cancel.test.ts`.
- M26: one workflow waits for an approval signal and then finishes. That proof is `tests/approval.test.ts`. The README records the local client and worker keys, the dashboard `RELAY_API_KEY`, and the two-tenant grant result. Stream catch-up, 1,000 runs, 10,000 runs, and Postgres CPU are not measured.
- M27: records that match the code. The study notes for `97cf173` now describe tenant keys, fairness, signals, waits, and cancellation. `docs/architecture.md` matches that behavior and still says Compose and the example app are absent. `CHANGELOG.md` records the user-visible Phase 4 behavior. `docs/adr/README.md` points 0001–0016 at the spec register and lists the written ADRs 0017 and 0018. No engine behavior changed.
- M28: measured capacity. `npm run capacity` is separate from `npm test`. On this machine it replayed 10, 100, 1,000, and 10,000 commands and activated 100, 1,000, and 10,000 one-step runs. The numbers, hardware, and Postgres version are in `docs/capacity.md`. Replay did not call the step function again. Stream catch-up completed for the 10-command history. Longer streams closed the SSE connection, and those catch-up times are not measured. Worker history and `GET /v1/runs/:id/events` order by the numeric event sequence. The proof is `tests/replay.test.ts`.

## Implemented

One sequential `ctx.step`. Crash before completion, lease expiry, a later attempt, replay without re-running the user function, and a duplicate completion receipt. Verified by the M1 exit test on real PostgreSQL (`tests/exit.test.ts`).

Heartbeat renewal, explicit release, and a server reaper that expires one due lease per transaction. Fencing proofs F02, F03, F04, F07, and F20 are in `packages/server/test/fencing.test.ts`. The SDK heartbeat loop is covered by `tests/heartbeat.test.ts`.

A fake provider in the test worker records invocations and effects. F05 is `tests/effects.test.ts`. Finish-run failpoints abort the transaction in `packages/server/sql/003_m3.sql`; F16 is `packages/server/test/atomicity.test.ts`. F18 is `packages/server/test/idempotency.test.ts`.

Structural replay compares the command at each position before calling the user function. F10, F11, and F12 are in `tests/structure.test.ts`.

`ctx.step.parallel` records the group and its children before any callback. Each child start, completion, and failure commits independently. F08 and F09 are in `tests/parallel.test.ts`. Phase 1 does not retry an exhausted child.

Trigger identity is the tenant plus the idempotency key. F17 is `packages/server/test/admission.test.ts`. `GET /v1/workflows` reports live compatible workers. F19 is in the same file. F21 rejects invalid state, a missing tenant, and direct application writes. A step stores its recovery ceiling at declaration. Exhaustion is `tests/recovery.test.ts`. The default ceiling is 100.

Phase 1 hooks for grant, heartbeat, declaration, and completion abort the open transaction through the existing failpoint helper. The server still does not expose a failpoint route. `lease.after-commit-before-response` is in the SDK, after the lease response. `GET /v1/runs/:id` and paginated event reads are on the HTTP server. `relay_verify_projections` compares commands, steps, attempts, business run fields, and the stream log with history. `relay_rebuild_projections` repairs those business rows from the event fold and rolls back if the comparison fails. It refuses a live lease and does not rewind coordination state. F22 is `packages/server/test/failover.test.ts`; the recovery-point disclosure is in `README.md`. The 100-run demo is `tests/demo.test.ts`. It prints measured activation times and history bytes for that run, separates callback counts from provider effects, and names the loads it did not measure. Invalid JSON is rejected with a path in `packages/protocol/test/json.test.ts`.

`stepCtx.emit` appends UTF-8 batches to `run_stream_events` on `POST /worker/v1/stream`. One unacknowledged buffer is in flight. It flushes at about 100 ms, at 4 KiB, and before completion or failure. Completion, failure, finish, and restart commit `step_completed`, `step_failed`, `run_terminal`, or `superseded` in the same transaction as the workflow transition. F23 through F28 are in `tests/stream.test.ts`. `GET /v1/runs/:id/stream` serves those rows as SSE. One shared `LISTEN` connection wakes readers; it is not a connection per client. `subscribe` reduces chunks and controls in order and drops a sequence it already applied. A `superseded` control invalidates only that attempt. F29 through F31 are in `tests/sse.test.ts`. A finished run's stream log expires seven days after completion. `relay_expire_streams` locks one due run, deletes its stream rows, and leaves `next_stream_seq` where it is. `GET /v1/runs/:id` still returns the output. A new batch is rejected and an identical operation receipt is replayed without allocating a sequence. F32 is `tests/retention.test.ts`. `ctx.step` accepts an explicit input, and a parallel child can too. The normalized value and its SHA-256 fingerprint are stored on the command and the step. A different fingerprint, or a switch between the plain step and the input-bearing step, raises nondeterminism before the stored result is returned and before another attempt starts. F13 is `tests/input.test.ts`. F12 remains the case that is not detected. `ctx.now(key)`, `ctx.random(key)`, and `ctx.uuid(key)` commit one server-generated value in `CommandRecorded`. `now` is database time truncated to milliseconds. `random` is Postgres `random()`, not a cryptographic API. F14 is `tests/helper.test.ts`. `ctx.sleep(key, durationMs)` commits `TimerScheduled` with a database wakeup. A positive sleep suspends the run without a worker slot. `relay_fire_one_timer` records `TimerFired` once from that wakeup. F35 is `tests/timer.test.ts`. An explicit retry policy commits one delay on `StepFailed` and wakes through `relay_fire_one_retry`. F33 and F34 are `tests/retry.test.ts`. `relay_failed_runs` lists failed runs. `lintWorkflow` checks workflow source text and does not follow indirect calls. The SDK and protocol packages expose types and pack `dist/src` only. `GET /v1/runs` lists those rows with state, workflow, and version filters, and `GET /v1/runs/:id/steps` returns attempts and an explicit input only when one was stored. `GET /v1/metrics` reads those same rows as Prometheus gauges, and a failed trace export does not undo a commit. The dashboard in `packages/dashboard` reads those HTTP APIs and the SSE stream. It attaches the client key from `RELAY_API_KEY` and does not show a signal or cancel button. `POST /v1/runs/:id/signal` stores a deduplicated signal. `ctx.waitForEvent` consumes the oldest matching signal or one recorded timeout. `POST /v1/runs/:id/cancel` races completion and rejects a later worker write. A lower-priority run can still wait behind a higher priority.

## Known issues

- Stream catch-up past the 10-command history is not measured. The SSE connection closes once 32 frames are queued.
- Recorded JSON ambiguities remain: the root counts as depth 1; unsafe integers are rejected rather than rewritten; SHA-256 is the receipt digest; no Unicode normalization.
- External effects are at least once. Provider deduplication is not an exactly-once guarantee.
